## 1. 아키텍처 패턴
### 1.1. 아키텍처 패턴의 개념
- **아키텍처** (Architecture)
	- 건물을 지을 때의 뼈대처럼, 소프트웨어 시스템의 **기본적인 구조**를 의미

- **아키텍처 패턴** (Architecture Pattern)
	- 수학의 '공식'이나 건물을 지을 때의 '가이드라인'과 같다.
	- 아키텍처를 설계할 때 참조할 수 있는 ==전형적인 해결 방식이나 예제==를 뜻한다.
	
	- 공식이 있으면 수학 문제를 빠르고 쉽게 풀 수 있듯,
	- 아키텍처 패턴이라는 가이드라인이 있으면 아무것도 없는 상태에서 설계하는 것보다 훨씬 쉽고 빠르게 시스템을 설계할 수 있다.

### 1.2. 아키텍처 패턴의 특징
- 소프트웨어 시스템 구조를 구성하기 위한 **기본적인 윤곽**을 제시한다.
- 각 서브 시스템들과 그 **역할**이 정의되어 있다.
- 서브 시스템들 사이의 **관계, 규칙, 지침** 등이 포함되어 있다.
- 다른 말로 **'아키텍처 스타일(Architecture Style)'** 또는 **'표준 아키텍처'**라고도 부른다.

### 1.3. 아키텍처 패턴 사용의 장점
- ==효율성 및 품질 향상==: 시행착오를 줄여 개발 시간을 단축하고, 고품질의 소프트웨어를 생산할 수 있다.
- **안정적인 개발**: 이미 검증된 구조를 바탕으로 개발하기 때문에 시스템이 안정적이다.
- **원활한 의사소통**: 이해관계자들이 공통된 아키텍처를 공유하므로 서로 간의 의사소통이 간편해진다.
- ==유지보수 용이==: 시스템 구조를 이해하기 쉬워, 처음 개발에 참여하지 않은 사람도 손쉽게 유지보수를 수행할 수 있다.
- **예측 가능성**: 개발을 시작하기 전에 시스템의 특성을 미리 예측할 수 있다.

### 1.4. 아키텍처 패턴의 주요 종류
- 4가지 주요 패턴
	- 레이어 패턴 (Layer Pattern)
	- 클라이언트-서버 패턴 (Client-Server Pattern)
	- 파이프-필터 패턴 (Pipe-Filter Pattern)
	- 모델-뷰-컨트롤러 패턴 (MVC, Model-View-Controller Pattern)

## 2. 레이어 패턴
- **레이어 패턴** (Layers pattern)
	- 시스템을 여러 개의 '계층(Layer)'으로 구분하여 구성하는 고전적인 아키텍처 방법

### 2.1. 계층 간의 역할과 상호작용
- **인접한 계층 간의 소통**
	- ==상호작용은 서로 마주 보는(인접한) 두 계층 사이에서만 이루어진다.==
	- (예: 1층과 7층이 직접 소통하지 않음)

- **역할**
	- **하위 계층**: 상위 계층에 서비스를 제공하는 **'서비스 제공자'** 역할
	- **상위 계층**: 하위 계층의 서비스를 사용하는 **'클라이언트'** 역할

### 2.2. 레이어 패턴의 장점
- ==유지보수의 용이성==
	- 특정 계층의 내용을 변경하더라도 서로 마주 보는 두 계층에만 영향을 미치므로 전체 시스템의 변경 없이 수정이 용이하다.

- **시스템 개선**
	- 특정 계층만 완전히 교체하여 전체 시스템의 성능이나 기능을 개선하는 것이 가능하다.

### 2.3. 대표적인 사례
- **OSI 참조 모델 (OSI 7계층)**
	- ISO에서 개발한 네트워크 통신 모델로,
	- 물리 계층부터 응용 계층까지 총 7개의 계층으로 나뉘어 있는 것이 레이어 패턴의 가장 대표적인 예시

## 3. 클라이언트-서버 패턴
- **클라이언트-서버 패턴** (Client-Server Pattern)
	- ==하나의 서버(Server) 컴포넌트와 다수의 클라이언트(Client) 컴포넌트==로 구성되는 시스템 구조
	- 여기서 '컴포넌트'란 독립적인 업무나 기능을 수행하는 실행 코드 기반의 모듈을 의미

### 3.1. 각 컴포넌트의 역할
- **서버 (Server)**
	- 데이터나 자원을 관리하고 클라이언트에게 서비스를 **제공**하는 역할
	- 언제, 어떤 클라이언트가 요청을 보낼지 모르기 때문에 ==항상 대기 상태(24시간 켜져 있음)를 유지==해야 한다.

- **클라이언트 (Client)**
	- 서버에 필요한 자원이나 데이터를 **요청**하고,
	- 서버로부터 응답을 받아 사용자에게 제공(사용)하는 역할을 한다.

### 3.2. 통신 방식 및 특징
- **단방향 소통 구조**
	- 사용자는 클라이언트를 통해서만 소통하며,
	- 클라이언트는 서버와만 통신한다.
	- ==클라이언트끼리는 서로 직접 통신하지 않는다.==

- **독립성**
	- 클라이언트와 서버는 데이터를 요청하고 응답받기 위해 동기화되는 시점을 제외하고는
	- 서로 **독립적**으로 각자의 기능을 수행한다.

### 3.3. 이해를 돕는 예시
- **포털 사이트 (예: 네이버)**
	- 사용자가 스마트폰이나 PC(클라이언트)를 통해 네이버(서버)에 접속하여 검색, 날씨, 뉴스 등의 데이터를 요청하고 화면으로 제공받는다.

- **온라인 게임**
	- 사용자는 게임 프로그램(클라이언트)을 통해 몬스터를 사냥하고,
	- 게임 회사(서버)는 사용자가 사냥할 수 있도록 몬스터를 계속해서 생성해 주는 독립적인 역할을 수행한다.

## 4. 파이프-필터 패턴
- 파이프-필터 패턴 (Pipe-Filter Pattern)
	- 공장의 조립 라인(컨베이어 벨트)에 비유할 수 있다.
	- 물건이 라인을 따라 이동하며 여러 작업자를 거쳐 완성되듯,
	- ==데이터가 여러 처리 단계를 연속적으로 거치며 가공==되는 아키텍처 패턴

### 4.1. 핵심 구성 요소
- **필터 (Filter)**
	- 데이터 스트림(연속적인 데이터 흐름)을 받아 실제로 **데이터를 처리(가공)**하는 컴포넌트
	- 각 처리 단계를 캡슐화(정보 은닉)하여 수행

- **파이프 (Pipe)**
	- 필터와 필터 사이를 연결하여 **데이터를 전송**하는 통로 역할

### 4.2. 주요 특징 및 장점
- ==높은 재사용성==: 필터 컴포넌트들은 각각 독립적인 기능을 하므로 다른 곳에서도 쉽게 재사용할 수 있다.
- ==뛰어난 확장성==: 공장 라인에 새로운 작업자를 투입하거나 빼는 것이 쉽듯, 새로운 필터를 추가하거나 기존 필터를 재배치하여 **다양한 파이프라인을 쉽게 구축**할 수 있다.

### 4.3. 단점
- **오버헤드 발생**: 필터 간에 데이터를 주고받을 때 데이터 형식을 변환해야 하는 경우, 이로 인해 시스템에 부담(오버헤드)이 발생할 수 있다.

### 4.4. 활용 분야 및 대표 사례
- **주요 활용**: 데이터 변환, 버퍼링, 동기화 작업 등에 주로 사용된다.
- **대표적인 사례**: **UNIX의 쉘(Shell)** 시스템이 파이프-필터 패턴을 적용한 가장 대표적인 예시이다.

## 5. 모델-뷰-컨트롤러(MVC) 패턴
- 모델-뷰-컨트롤러(MVC) 패턴
	- 서브시스템을 **모델(Model), 뷰(View), 컨트롤러(Controller)**라는 3개의 독립적인 부분으로 나누어 구조화하는 아키텍처 패턴

### 5.1. 3가지 핵심 구성 요소
- **모델 (Model)**
	- 시스템의 핵심 기능과 ==데이터를 보관하고 관리==하는 역할

- **뷰 (View)**
	- 처리된 정보나 결과물을== 사용자가 볼 수 있도록 화면에 표시==해 주는 역할
	- (사용자 인터페이스, UI)

- **컨트롤러 (Controller)**
	- 사용자로부터 ==입력을 받아 처리==하고,
	- 그 명령에 따라 모델의 상태를 바꾸거나 뷰를 제어하는 역할

### 5.2. 작동 흐름
- 사용자가 어떤 동작(입력)을 하면
- ➔ **컨트롤러**가 이를 받아 처리하고
- ➔ **모델**의 데이터를 갱신한다.
- ➔ 변경된 모델의 정보는 **뷰**로 전달되어
- ➔ 사용자에게 새로운 화면으로 보여진다.

### 5.3. 주요 특징 및 장점
- ==독립성과 개발 편의성==
	- 각 부분(M, V, C)이 별도의 컴포넌트로 분리되어 있어 서로 영향을 주지 않는다.
	- 따라서 여러 개발자가 **동시에 개별적으로 개발 및 유지보수**를 할 수 있어 효율적이다.

- **다양한 화면(View) 생성 가능**
	- 하나의 동일한 '모델(데이터)'을 가지고 여러 형태의 '뷰(화면)'를 만들어 낼 수 있다.

- **대화형 애플리케이션에 최적화**
	- 사용자의 입력에 즉각적으로 반응하고 데이터를 처리해 보여줘야 하는 **온라인 쇼핑몰, 스마트폰 앱 등 대화형 애플리케이션**을 개발하는 데 매우 적합하다.
