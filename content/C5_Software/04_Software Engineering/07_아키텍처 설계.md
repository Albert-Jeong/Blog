> 아키텍처 설계와 패턴

## 0. 아키텍처 개요
- **아키텍처**
	- *복잡하고 큰 소프트웨어를 컴포넌트로 구성하고 관계를 정의하는 것*
	- 시스템 구조를 확립하는 소프트웨어 개발의 중심축으로,
	- 설계부터 테스팅까지 모든 단계에 영향을 주는 초기 의사결정의 핵심이다.

- **아키텍처 설계**
	- *시스템을 다루기 쉽고 미래의 변경에 잘 대처할 수 있는*
	- 서브시스템 수준의 덩어리화(chunking) 작업으로,
	- 구성 요소의 역할과 요소 간 관계에 집중한다.

### 0.1. 추가 강의자료
- **소프트웨어 아키텍처**
	- 나중에 변경하기 힘들고, 소프트웨어 시스템을 개발하는데 필수
	- 세부 사항들은 아키텍처가 아니라 설계(Design) 요소

- **소프트웨어 아키텍처 다이어그램**
	- 소프트웨어의 구조를 정의
	- 사용자 인터페이스, 서비스, 데이터베이스, 통신 프로토콜 등

- **소프트웨어 아키텍처 차원**
	1. **아키텍처 특성**: 아키텍처가 지원해야 하는 시스템의 측면 (확장성, 테스트 용이성, 가용성 등)
		- 소프트웨어 시스템 아키텍처의 기반을 형성한다.
		- 어떤 특성이 중요한지 기준이 필요하다. (아키텍처 특성에 따라 달라짐)
		- 아키텍처 특성은 비기능 요구사항, 시스템 품질 속성 등이라고 불리기도 함
		- 시스템의 성공에 중요한 역할을 하는 기능
	2. **아키텍처 결정**: 시스템에 장기간 혹은 상당한 시사점을 갖는 중요한 결정 (예: 사용하는 데이터베이스의 종류, 시스템에 포함되는 서비스 개수, 소통 방법 등)
		- 시스템의 구조적 측면에 관한 선택 -> 장기적인 영향
		- 시스템의 사용자 인터페이스가 데이터베이스와 직접 통신하지 않고 하위 서비스를 통해서 데이터를 접근하도록 결정
	3. **논리적 컴포넌트**: 시스템 기능의 구성 요소와 그것들이 어떻게 상호작용하는지 설명 (예: 시스템의 컴포넌트 등)
		- 시스템의 구성요소
		- 주로 디렉터리 또는 네임스페이스로 표현
		- 잘 정의된 역할과 책임을 가져야 한다.
	4. **아키텍처 스타일**: 소프트웨어 시스템의 물리적 구조화 형태
		- 각기 다른 고유한 특성들로 소프트웨어 시스템의 전반적인 모습과 구조를 정의 (마이크로서비스, 레이어드, 이벤트 기반)
		- 아키텍처를 전환하는 것은 쉽지 않기 때문에 처음부터 올바른 선택을 해야 함

- **아키텍처 vs. 설계**
	- 아키텍처는 외관보다는 구조에 중점을 둠
	- 설계는 구조보다는 외관에 더 중점을 둠

- **아키텍처와 설계의 스펙트럼**
	1. **전략적 결정 vs. 전술적 결정**
		- 전략적 결정: 장기적으로 미래의 행동이나 결정에 영향 (전략적 결정일수록 좀 더 아키텍처적인 결정에 가까움)
		- 전술적 결정: 단기적이고 일반적으로 다른 행동이나 결정에 독립적
	2. **구축/변경에 얼마나 노력이 드는지?**
		- 아키텍처 결정은 구축/변경에 많은 노력
		- 설계 결정은 상대적으로 적은 노력
		- 높은 수준 vs. 낮은 수준
			- 소프트웨어 아키텍처는 변경하기 어려운 것들이다. (마틴 파울러)
			- 나중에 변경하기 어려울 수록 아키텍처 쪽에 가깝다.
	3. **중대한 트레이드오프가 있는지?**
		- 트레이드오프의 중요성에 따라서 이 결정이 아키텍처에 가까운지 설계에 가까운지 결정하는데 도움
		- 트레이드오프가 중대할수록 아키텍처에 가깝고, 덜 중대할수록 설계 쪽에 가깝다.

- **디자인 패턴**
	- 아키텍처 구성 요소 안에서 이루어지는 상세 설계에서 필요한 지식
	- 설계 작업에서 마주하는 많은 문제들에 대한 정답 제공 -> 디자인 작업 단순화

## 1. 아키텍처 설계
### 1.1. 아키텍처 구축 절차
1. 요구 사항 분석
2. → 아키텍처 분석
3. → 아키텍처 설계
4. → 검증 및 승인

### 1.2. 아키텍처 드라이버
1. **설계 목적**
	- 달성하려는 비즈니스 목표를 먼저 명확히 설정해야 합니다.

2. **품질속성**
	- 이해당사자의 필요를 얼마나 잘 만족시키는지를 나타내는 측정/테스트 가능한 시스템 속성이다.
	- 품질속성 시나리오는 6가지 요소(자극, 자극원, 반응, 반응측정, 환경, 대상)로 구성되며,
	- 우선순위는 유틸리티 트리(Utility Tree)로 표현한다.

3. **최우선 기능** 
	- 비즈니스 목적 달성에 중요하거나 기술 난이도가 높은 기능으로,
	- 일반적으로 전체 유스케이스의 약 10%이다.

4. **아키텍처 관심사**
	- 전통적으로 요구사항으로 표현되지 않는 추가적인 설계 고려 사항으로,
	- 일반 관심사(구조 수립, 배포 등)와 특별 관심사(인증, 캐싱, 로깅 등)로 나뉜다.

5. **제약사항**
	- 아키텍트가 통제할 수 없는 결정사항
	- (필수 기술, 법규, 마감 시간 등)

### 1.3. 아키텍처 4+1 관점 (Philippe Kruchten)
|         관점          |   대상자    |               내용               |
| :-----------------: | :------: | :----------------------------: |
|    Usecase View     |   사용자    |    시스템이 제공하는 기능, 다른 관점의 근간     |
|    Logical View     |   설계자    |    클래스 종류와 관계 (Module View)    |
| Implementation View |   개발자    | 모듈 구성과 배포 단위 구조 (Module View)  |
|    Process View     | 시스템 통합자  |    실행 시점의 동적 행위 (C&C View)     |
|   Deployment View   | 시스템 엔지니어 | 컴포넌트의 물리적 배치 (Allocation View) |

## 2. 아키텍처 스타일
- **아키텍처 스타일**
	- *구성 요소들의 역할과 관계가 잘 알려진 공통 유형들*
	
	- *유사한 구조와 상호작용 패턴을 공유하는 시스템*
	- *구성 요소 유형에 대한 설명 및 런타임 제어, 데이터 전송에 대한 패턴*
	- *시스템을 이루는 컴포넌트의 유형과 상호작용 패턴에 대한 제약*
	
	- 정의된 컨텍스트 안에 반복적으로 나타나는 설계 문제에 대한 개념적 솔루션

- *시스템 타입*
	- 시스템의 타입은 설계 방법과 아키텍처 스타일 선택에 영향
	- 대화형 시스템
	- 이벤트 중심 시스템
	- 변환 시스템
	- 객체 영속 시스템

### 2.2. 클라우드 아키텍처
> 클라우드는 고가용성·탄력적 확장성·비용 효율을 위해 컨테이너, MSA 등 클라우드 네이티브 기술을 활용한다.

- **핵심 요소**
	- **마이크로서비스(MSA)**: 독립 배포 가능한 작은 서비스 단위로 분해
	- **서버리스(Serverless)**: 서버 관리 없이 클라우드가 자동 처리 (FaaS / BaaS)
	- **컨테이너**: Docker를 이용해 어디서나 동일하게 실행되는 가상화 기술
	- **오케스트레이션**: Kubernetes로 컨테이너 배포·스케일링·관리 자동화
	- **API Gateway**: 단일 진입점 제공, 보안·인증·트래픽 제어
	- **서비스 메시**: 내부 서비스 간 통신 관리 (Istio 기반)
	- **DevOps / CI/CD**: 코드 관리부터 배포까지 파이프라인 자동화

### 2.3. 3가지 아키텍처 비교
|   구분    |    모놀리식     |    마이크로서비스    |        서버리스        |
| :-----: | :---------: | :-----------: | :----------------: |
|   구조    |  단일 코드베이스   |  서비스별 분산 구조   | 이벤트 기반 Function 단위 |
|   확장성   | 전체 확장 (비효율) |  필요한 서비스만 확장  |       자동 확장        |
|   배포    |   전체 재배포    |  서비스별 독립 배포   | Function 단위 즉시 배포  |
|   비용    |    고정 비용    | 인프라 관리 비용 높음  |     사용한 만큼 지불      |
| 적합 프로젝트 | 빠른 출시, 소규모  | 독립 기능, 높은 확장성 | 이벤트 기반, 트래픽 변동 많음  |
> **하이브리드 모델**: 서버리스 + 컨테이너 기반 MSA를 결합해 효율성을 극대화하는 현실적인 선택

### 2.4. 아키텍처 스타일 선택 기준
- 확장성(Scalability), 유지보수성(Maintainability), 성능(Performance), 보안(Security), 비용(Cost)

### cf. 클린 아키텍처
- 유지보수, 확장성, 테스트 용이성을 높이기 위한 아키텍처 (Robert C. Martin)
- 컴포넌트가 프레임워크, 유틸리티, UI 라이브러리, 테스트 방법 등에 대해서 독립적으로 개발, 수정, 배포 (SOLID 구성 원칙)
- 클린 아키텍처의 4가지 계층
	- 엔터프라이즈 비즈니스 규칙
	- 유스케이스
	- 인터페이스 어댑터
	- 프레임워크와 드라이버
