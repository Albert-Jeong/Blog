## 정리
- 쓰레드
	- 프로세스 내에서 자원을 공유하면서 독립적인 실행 흐름을 갖는 경량 단위
	- 생성 비용이 낮고 응답성이 좋아 병렬 처리와 I/O 중첩에 유리하다.

- ULT는 빠르지만 블록 문제가 있고, KLT는 진정한 병렬성을 제공하지만 오버헤드가 있다.

- 멀티코어 환경에서도 Amdahl의 법칙과 오버헤드로 인해 무한정 성능이 향상되지는 않는다.

## 도입부
### 1. 모듈 간 통신 방법
> 프로젝트를 모듈 단위로 설계할 때, 모듈의 위치에 따라 통신 방법이 달라진다.

1. **하나의 프로세스 내부**
	- 함수를 직접 호출
	- (메모리를 공유하여 별도의 통신 기법 불필요)

2. (같은 컴퓨터) **여러 프로세스**
	- 프로세스는 메모리를 공유하지 않으므로 OS가 제공하는 ==IPC==(Inter-Process Communication) 필요
	    - **Shared Memory**: 메모리 영역 공유 → 빠르지만 동기화 문제
	    - **Message Passing**: 메시지 송수신 → 안전하고 단순
	    - **Semaphore**: 통신이 아닌 동기화 도구 (공유 자원 접근 제어)
	    - **Pipe**: 파일처럼 동작하는 단방향 채널

3. **다른 노드(컴퓨터)에 있는 프로세스**
	- OS가 IPC 중재 불가 → ==네트워크 API== 사용
	    - **Socket**: 저수준 통신, IP+포트 연결, TCP/UDP 선택
	    - **RPC**: 원격 함수를 로컬 함수처럼 호출 (내부적으로 소켓 사용)

### 2. 소프트웨어 개발 3요소
1. 기능 정확도 (입문 단계)
2. 성능 최적화 (경쟁력)
3. Secure Coding

### 3. 프로세스 vs 스레드
- **멀티 프로세스** (`fork()` + `exec()`)
	- 각 프로세스가 독립된 메모리 공간 보유
	- 통신 시 IPC 필요 → 무거움

- **멀티 스레드** (`pthread_create()`)
	- 같은 프로세스 내에서 메모리 공유
	- Process Context 오버헤드 없음 → 가볍고 빠름

- **핵심 포인트**
	- 한 프로세스 안에서 동시 작업이 필요할 때,
	- 무거운 멀티 프로세스 대신 메모리를 공유하는 스레드를 사용하면 효율적이다.

## 1. 프로세스와 쓰레드
### 1.1. 프로세스의 정의
- **프로세스**
	- **실행 중인 프로그램(A program in execution)**

- **프로세스의 두 가지 핵심 역할**
	1. **자원 소유권(resource ownership)** 측면에서 메모리(코드, 데이터, 스택), 파일, signal, IPC 등의 자원을 소유한다.
	2. **수행/스케줄링(execution/scheduling) 개체**로서 CPU 레지스터 정보와 스케줄링 정보를 가진다.

### 1.2. 태스크와 쓰레드로의 분리
> 현대 OS에서는 프로세스가 두 객체로 분리되어 관리된다.

1. **태스크**(Task) / **프로세스**(process)
	- Resource Container 역할
	- (사용자 문맥, 시스템 문맥)

2. **쓰레드**(Thread) / **경량 프로세스**(lightweight process)
	- 제어 흐름 역할
	- (실행 정보, 레지스터 문맥)

### 1.3. 프로세스 이미지 구성
- 프로세스 이미지
	- PCB(프로세스제어블록)
	- 텍스트(코드/명령어)
	- 데이터(전역변수)
	- 힙(동적 메모리 할당)
	- free area
	- 스택(지역변수/매개변수)

> -> 세그먼트 단위

- *실제로는 페이지 단위 (메모리 곳곳에 흩어짐 - 7/8장 참고)*

### 1.4. 멀티쓰레딩 환경에서의 자원 분리
- 스레드 생성 및 처리 흐름
	1. creating program: 메인 프로그램에서 이벤트(클라이언트 연결 등) 감지
	2. `pthread_create(fn())`: 해당 이벤트를 처리할 새 스레드 생성
	3. created thread: 스레드 생성 완료
	4. `processfd()`: 생성된 스레드 내에서 소켓(File Descriptor)을 실제로 처리

- **쓰레드 모델**은 4가지로 구분된다.
	1. 단일 프로세스/단일 쓰레드
	2. 단일 프로세스/멀티 쓰레드
	3. 멀티 프로세스/프로세스당 단일 쓰레드
	4. 멀티 프로세스/프로세스당 멀티 쓰레드

- **태스크(프로세스) 차원**
	- 가상 주소 공간, 처리기/다른 프로세스/파일/I/O 자원에 대한 접근 제어를 관리한다.
- **쓰레드 차원**
	- 실행 상태(수행/준비/블록), CPU 레지스터 문맥, 실행 스택, 지역 변수용 정적 저장소를 각자 가진다.
	- 한 프로세스 내의 모든 쓰레드는 그 프로세스의 자원을 공유한다.

- 각 쓰레드는 프로세스 자원(주소 공간, 파일, I/O 등)을 **공유**하지만, ==아래 항목은 개별적으로 유지==한다. (==Thread별로 유지해야 하는 자료구조==)
	1. 실행 상태: 수행(Running), 준비(Ready), 블록(Blocked) 등
	2. 쓰레드 문맥: ==CPU 레지스터 값==
	3. 실행 스택: 함수 호출 및 흐름 제어를 위한 ==Stack==
	4. ==TSD==(Thread-Specific Data): 지역 변수 저장을 위한 전용 저장소
	5. TCB(Thread Control Block): 쓰레드 ID, 상태, 우선순위 등을 담은 관리 정보

### 1.5. Creation Overhead & Pool
1. 비용 비교 (생성/종료 오버헤드)
	- **프로세스 방식**: 1개 생성/종료 비용이 1,500이며, 100번 반복 시 **총 150,000** 소모
	- **쓰레드 방식**: 프로세스 초기 비용(1,000) + 쓰레드 생성/종료(150) × 100 = **15,100**
	- 결론: 쓰레드가 프로세스보다 약 10배 저렴하지만, 여전히 매번 생성/종료하는 비용이 누적됨

2. 풀(Pool)의 등장 배경
	- "100번의 작업 동안 생성/종료를 아예 하지 않는다면?"이라는 질문에서 출발. 미리 만들어 두고 재사용하면 생성/종료 비용을 거의 제거할 수 있음.

3. 풀의 종류
	- **프로세스 풀**(Process-pool)
		- 독립된 메모리 공간을 가진 프로세스들을 미리 생성
	- **쓰레드 풀**(Thread-pool)
		- 하나의 프로세스 내에서 자원을 공유하는 쓰레드들을 미리 생성

4. 풀의 동작 3단계
	1. **초기화**: 시작 시 미리 생성 (생성 비용은 이때 한 번만)
	2. **작업 할당**: 들어온 일을 Idle 상태의 자원에 배정
	3. **반환**: 작업 완료 후 종료하지 않고 풀에 반납 → 재사용

|    방식    |          비용           |            (100개 작업) 총 비용             |
| :------: | :-------------------: | :-----------------------------------: |
|    일반    |    1000 / 1 / 500     |       1500 × 100 = **150,000**        |
|   쓰레드    | 1000 / (100 / 1 / 50) |    1,000 + 150 × 100 = **15,100**     |
| 5개 쓰레드 풀 | 1000 / (100 / 1 / 50) | 1,000 + 5 × 150 + 100 × 1 = **1,850** |
> (5개 쓰레드 풀, 100개 작업 기준) → 생성/종료 비용이 0에 수렴

5. 윈도우 서버 프로그래밍 발전사
	1. **초기**: WSAAsyncSelect (메시지 기반)
	2. **중기**: WSAAsyncEvent (이벤트 신호 기반)
	3. **발전**: Overlapped I/O (비동기 결과 통보)
		- Event 방식 (I), Completion Routine 방식 (II)
	4. **완성**: **IOCP**(I/O Completion Port) = Thread Pool + 비동기 I/O

### 1.6. 쓰레드의 장점
1. 프로세스에 비해 **생성/종료 시간과 비용이 절약**된다.
	- 50,000번 생성 기준으로 fork()가 41~104초 걸릴 때 pthread_create()는 0.66~2.03초로 매우 빠르다.

2. **병렬처리**에 적합
	- **멀티프로세서**를 효율적으로 사용할 수 있고,
	- listening thread와 responding threads로 구성된 **병행 서버** 구현에 유리하다.

3. I/O 작업과 컴퓨팅 작업이 병행적으로 실행되어 **응답시간이 향상**된다.
	- (예: 워드 프로세서, 스프레드시트)

### 1.7. 활용 사례
- **웹 서버**
	- Dispatcher thread가 요청을 받아 Worker thread에 분배하고,
	- Worker는 캐시 확인 후 페이지를 반환

- **RPC(원격 프로시저 호출)**
	- 여러 쓰레드가 각각 다른 서버에 RPC 요청을 보내 응답 대기 시간을 중첩

#### cf. TCP 소켓 통신의 서버/클라이언트 흐름 예
> 흐름 과정에서 **bind()가 명시적/암묵적으로 어떻게 호출되는지**

1. **서버의 accept()는 내부적으로 새로운 소켓(nsd)을 만들어 클라이언트와 1:1 통신을 담당시킨다.**
2. **클라이언트는 명시적으로 bind()를 호출하지 않지만, connect() 내부에서 자동으로 임시 포트가 bind된다.**

```c
// ===== Server =====
sd = socket(AF_INET, SOCK_STREAM, 0);		// TCP 소켓 생성 (listening socket)
bind(sd, IP, Port);							// 서버의 IP/Port에 결합
listen(sd, backlog);						// 연결 요청 대기 큐 생성

while (1) {
	nsd = accept(sd, &client_addr, &len);	// 클라이언트 연결 수락
	// 내부적으로 새 소켓 nsd 생성:
	//     nsd = socket() → 통신 전용 소켓
	//     bind(nsd, server_IP, same_Port) → 서버 주소에 자동 결합
	//     (즉, listening socket과 동일한 포트를 공유하되,
	//     4-tuple [src IP/Port, dst IP/Port]로 구분됨)
	
	if (fork() == 0) {						// 또는 pthread_create()
		close(sd);							// 자식은 listening socket 불필요
		svc(nsd);							// 클라이언트 서비스 처리
		close(nsd);
		exit(0);
	}
	close(nsd);								// 부모는 통신 소켓 불필요, 다시 accept 대기
	}
```

```c
// ===== Client =====
sd = socket(AF_INET, SOCK_STREAM, 0);		// TCP 소켓 생성
connect(sd, server_IP, server_Port);		// 서버에 연결 요청
// 실질적으로 connect() 안에서 자동으로:
//     bind(sd, INADDR_ANY, 0) → OS가 임시 포트(ephemeral port) 자동 할당
//     (클라이언트는 굳이 자기 포트를 지정할 필요가 없으므로)

svc(sd);									// 서버와 통신
close(sd);
```

- 서버 측: accept()의 동작
	- `sd`(listening socket)는 **연결을 받기만 하는 전용 소켓**
	- `accept()`는 새 연결이 들어올 때마다 **새로운 소켓 `nsd`를 생성**하여 반환
	- `nsd`는 해당 클라이언트와의 **1:1 통신 전용 소켓**
	- 즉, 같은 포트(예: 80)에 여러 클라이언트가 붙어도 각각 별도의 nsd로 구분됨 (4-tuple로 식별)

- 클라이언트 측: 암묵적 bind
	- 클라이언트는 자신의 포트 번호를 신경 쓸 필요가 없음
	- `connect()` 호출 시 OS가 **사용 가능한 임시 포트(ephemeral port)를 자동 할당**하여 내부적으로 bind
	- 그래서 클라이언트 코드에는 명시적 bind()가 없음

- 멀티쓰레딩/멀티프로세싱과의 연결
	- `svc(nsd)`를 처리하는 부분에서 보통 fork() 또는 pthread_create()를 사용
	- 한 서버가 동시에 여러 클라이언트를 처리할 수 있는 이유 = 새 nsd마다 새로운 쓰레드/프로세스 배정
	- 여기서 앞서 정리한 **쓰레드 풀(Thread Pool)** 개념이 활용됨 (매번 생성/종료 대신 미리 만들어둔 풀에서 꺼내 씀)

## 2. 프로세스 및 쓰레드 생성 함수
### 2.1. fork() 시스템 호출
```c
/* test_fork2.c: 같은 변수 접근 */
#include <sys/types.h>
#include <unistd.h>
// 함수 원형: pid_t fork(void);

int glob = 6;
char buf[] = "a write to stdout\n";

int main(void) {
	int var = 88;
	pid_t pid;
	
	if (write(STDOUT_FILENO, buf, sizeof(buf)) != sizeof(buf)) {
		perror(“write error”);
		exit(1);
	}
	printf("before fork\n"); /* we don't flush stdout */
	
	if ( (pid = fork()) < 0) {
		perror(“fork error”);
		exit(1);
	} else if (pid == 0) { // 자식 프로세스: 0 반환
		/* modify variables */
		glob++;
		var++;
	} else { // 부모 프로세스: 자식 프로세스의 PID 반환 (non-zero)
		sleep(2);
	}
	printf("pid = %d, glob = %d, var = %d\n", getpid(), glob, var
	// 부모는 glob=6, var=88
	// 자식은 glob=7, var=89
	
	exit(0);
}
```

- 부모와 자식은 같은 변수를 각자의 주소 공간에 복사하여 독립적으로 수정한다.

### 2.2. pthread_create()
- **pthread** (POSIX Thread)
	- IEEE POSIX 1003.1c 표준``
	- Linux의 Pthread는 **커널 수준 쓰레드**이며 `clone()` 시스템 호출로 구현된다.

- **fork() vs pthread의 핵심 차이**
	- 예제에서 모든 쓰레드가 전역변수 glob을 공유하여 7, 8, 9, 10, 11로 증가하지만,
	- 지역변수 var는 각자 가지므로 모두 89로 동일하게 출력된다.

```c
#include <pthread.h> // gcc test.c -o test -lpthread

#define NUM_THREADS 5

void *PrintHello(void *threadid) {
	printf("Hello World! It’s me, thread #%ld \n", threadid);
	pthread_exit(NULL);
}

int main (int argc, char *argv[]) {
	pthread_t threads[NUM_THREADS];
	int rc, t;
	
	for (t=0;t < NUM_THREADS;t++) {
		printf("In main: creating thread %d\n", t);
		
		// 쓰레드 생성 (&thread, NULL, 함수명, 인자)
		rc = pthread_create(&threads[t], NULL, PrintHello, (void *)t);
		
		if (rc) {
			printf("ERROR; return code from pthread_create() is %d\n", rc);
			exit(-1);
		}
	}
	pthread_exit(NULL); // 쓰레드 종료
}
```

## 3. 쓰레드의 유형
|        유형        |              설명               |              장점              |                 단점                 |
| :--------------: | :---------------------------: | :--------------------------: | :--------------------------------: |
| **사용자 수준 (ULT)** | 쓰레드 라이브러리가 관리, 커널은 쓰레드 존재를 모름 | 모드 전환 오버헤드 없음, 모든 OS에서 실행 가능 | 한 쓰레드 블록 시 전체 프로세스 블록, 다중처리기 활용 불가 |
| **커널 수준 (KLT)**  |        커널이 직접 관리·스케줄링         |         다중처리기 활용 가능          |           모드 전환 오버헤드 발생            |
|    **결합 방식**     |    ULT+KLT 혼합 (Solaris 등)     |         두 방식의 장점 결합          |               구현 복잡                |

### 3.1. 사용자 수준 쓰레드 (ULT)
- ==응용 프로그램이 쓰레드 라이브러리를 통해 모든 쓰레드 관리==(생성, 제거, 동기화, 스케줄링, 문맥교환)를 책임지며, ==커널은 쓰레드의 존재를 모른다.==
- 예: cthread, pthread

- **장점**
	- 쓰레드 교환 시 커널 모드 권한이 불필요(모드 전환 오버헤드 절약)
	- 응용에 맞는 스케줄링 적용 가능
	- 모든 OS에서 수행 가능

- **단점**
	- 한 쓰레드가 블록 시스템 호출을 하면 프로세스 내 모든 쓰레드가 블록됨
	- 다중처리기 장점을 살리지 못함
	- 커널 루틴 자체는 멀티쓰레딩 불가

### 3.2. 커널 수준 쓰레드 (KLT)
- ==커널이 직접 프로세스와 쓰레드의 문맥 정보를 관리하고 스케줄링도 커널 수준에서 수행==한다.
- 예: Windows

### 3.3. 결합 방식 (Combined)
- ULT와 KLT를 혼합한 방식
- 예: Solaris

### 3.4. 쓰레드와 프로세스의 관계
- **1:1**: 대부분의 UNIX
- **M:1**: Windows NT, Solaris, Linux, MACH
- **1:M**: Ra(Clouds), Emerald (쓰레드가 프로세스 간 이동 가능)
- **M:N**: TRIX

## 4. 멀티코어와 멀티쓰레딩
### 4.1. Amdahl의 법칙
$$\text{속도향상} = \frac{1}{(1-f) + \frac{f}{N}}$$
- 여기서 $f$는 병렬화 가능한 코드 비율, $N$은 병렬 처리기 수
- 순차 실행만 가능한 부분 $(1-f)$가 전체 성능 향상의 한계를 결정한다.

### 4.2. 멀티코어가 성능에 미치는 영향
- 이상적으로는 처리기 수에 비례하여 성능이 향상되지만,
- 실제로는 **오버헤드**(멀티프로세서간 통신, 작업 분배, 캐시 일관성 유지 등)로 인해 일정 처리기 수 이상에서는 오히려 성능이 저하될 수 있다.
- 오버헤드가 5%면 약 5개 처리기에서 최고 성능, 20%면 더 일찍 한계에 도달한다.

## cf. Linux의 Process Context (프로세스 문맥)
- 프로세스 문맥
	- 운영체제가 프로세스를 관리하고 실행하기 위해 필요한 모든 정보
	- 크게 **3가지 영역**으로 구성

### 1. System Context (시스템 문맥)
운영체제가 프로세스를 관리하기 위해 커널 영역에 유지하는 자료구조들이다.

- **Task Structure**
	- 프로세스의 핵심 정보를 담고 있는 구조체로, 시스템 문맥의 중심 역할을 한다.
	- 다른 자료구조들을 가리키는 포인터를 포함한다.
- **File Table & fd (File Descriptor)**
	- 프로세스가 열어놓은 파일들을 관리하는 테이블이다.
	- task structure가 파일 디스크립터 배열을 가리키고, 이것이 다시 file table을 참조한다.
- **Segment Table**
	- 프로세스의 메모리 세그먼트 정보를 담고 있으며, page table을 가리킨다.
- **Page Table**
	- 가상 메모리 주소를 실제 물리 메모리 주소로 변환하는 정보를 담고 있다.

### 2. Hardware Context (하드웨어 문맥)
CPU의 레지스터 값들을 저장하는 영역으로, **TSS(Task State Segment)** 라고 불린다.
프로세스가 실행 중일 때의 CPU 상태를 보존하여 문맥 교환(context switching) 시 사용된다.

- 주요 레지스터
	- `eip`: 다음에 실행할 명령어의 주소 (Instruction Pointer)
	- `sp`: 스택 포인터 (Stack Pointer)
	- `eflags`: 플래그 레지스터 (CPU 상태 정보)
	- `eax`: 범용 레지스터 (산술 연산 등에 사용)
	- `cs`: 코드 세그먼트 레지스터

Task Structure와 양방향으로 연결되어 프로세스 전환 시 레지스터 값들을 저장하고 복원한다.

### 3. Memory Context (메모리 문맥)
프로세스가 실제로 사용하는 메모리 공간이다.

- **Memory (주기억장치)**: page table을 통해 매핑된 실제 물리 메모리 영역으로, 프로세스의 코드와 데이터가 적재된다.
- **Disk (swap or a.out)**: 메모리에 올라와 있지 않은 부분은 디스크의 스왑 영역이나 실행 파일(a.out)에 존재한다. 필요할 때 메모리로 적재된다.

### 정리
세 가지 문맥이 유기적으로 연결되어 하나의 프로세스를 구성하며,
Task Structure를 중심으로 system context의 자료구조들이 연결되고,
hardware context(TSS)와 memory context가 함께 묶여 프로세스의 완전한 실행 환경을 형성한다.
이러한 구조 덕분에 운영체제는 여러 프로세스를 효율적으로 전환하며 실행할 수 있다.
